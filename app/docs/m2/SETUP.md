User authorized local M2 on 2 October 2026 while providing service keys later. M1's local gate passed; its live gates remain pending. ## Behaviour

Each application owns its UUID, immutable submitted profile/job title/policy version, stage, status, version, deadline and event history. Candidate list queries explicitly filter the current Auth UUID; staff queues use live assignment/membership/AAL2 checks. Candidate DTOs exclude internal notes and evidence contents. UUID deep links fetch authorized history and cannot claim another candidate's identity.

P0 apply → P1 resume screening → P2 identity → P3 quiz → P4 approved background requirements → P5 human decision → P6 human interview scheduling. Advance/skip never means hire. Shortlist is available only at P5 with all required, unexpired, non-revoked evidence. A P6 shortlisted application can enter `interview_ready`; actual slot/interviewer/calendar confirmation remains M8. Withdrawal, rejection and job closure block scheduling. Closing a job atomically closes active applications and sends in-app notification records.

Resume references freeze when the human moves P1 to P2; replacement uploads are then denied. Existing submitted profile snapshots remain intact. Legacy applications receive the conservative default policy; their historic job title/profile is not reconstructed or silently rewritten. Unresolved M1 imports remain on hold until reviewed reconciliation.

Staff actions require AAL2, assigned job and active HM/admin membership, a reason and evidence references. References must belong to the same application: its immutable submission UUID, an unexpired document UUID or a reviewed-evidence UUID. The default submission reference supports a human review; it cannot satisfy identity/quiz/background requirements. Rejection reasons are candidate-visible. Private-note text is stored separately and its public event contains only a generic marker. Job closure requires an explicit reason/confirmation dialog.

Policy is configured by the operator, not by candidate JSON. Default identity and quiz gates are required, background checks default to none, skips/exceptions default to none. `allowed_skips` do not bypass a required gate. Approved credit/criminal exceptions require an authorized admin reviewer, purpose/employer-specific consent matching the configured `consent_versions` entry and an explicit policy allowance. Evidence requires a live reviewer membership, method and expiry; mock evidence satisfies only an explicitly demo-only policy. Consent revocation blocks subsequent progression and interview entry. M3–M5 must publish the correct current consent versions in job policy before real capture; M2 does not supply a legal approval or consent text.

M3–M5 populate `kerja_private.pipeline_evidence` through their qualified workflows. M2 exposes no browser endpoint to manufacture passing evidence. Until those modules exist, required stages are visibly blocked. The offline gate seeds labelled synthetic evidence solely in an ephemeral database. That is not verification of a real person.

Every transition takes an expected version and a caller-scoped idempotency key. The database serializes operations per job/application and commits state/event/outbox together. Repeating an identical key returns its result; changing the request under the same key is rejected. A stale version requires refresh. Reopening a withdrawn P0 application is an explicit staff action in the same cycle; screened/terminal applications cannot be silently reopened. A reviewed new job cycle permits a new independent application.

The legacy graph/tool routers remain retired and cannot mutate candidate-wide state, reject or dispatch email. PipelineService accepts only canonical application UUIDs and the verified actor. Recommendations do not create human approvals; reconnecting graph computation is later work and must use this context/service boundary. Original graph feature source remains preserved.

## Run / demo / rollback

Use M1 SETUP.md for server environment and local commands. Apply M1 then M2 to a backed-up isolated Supabase project after keys arrive. Operator creates employer, jobs, assignments and confirmed A/B/HM accounts. Staff enroll/verify MFA in the existing workspace before their queue appears. No client-side demo accounts exist.

Candidate A applies to X/Y and B to X: three UUIDs. HM advances A/X to resume review and pauses B/X; A/Y stays independent. Upload a synthetic PDF, review it and advance A/X to identity; identity remains blocked without M3 evidence. Try guessed UUIDs/unassigned jobs/candidate decisions and confirm denial. Withdraw/reopen A/Y at P0; close a separate job and confirm active applications stop. Use the offline suite to demonstrate labelled synthetic full prerequisite progression and expired/revoked gate denial.

Dashboard provides status/stage/deadline filtering/sorting, 50-row pagination, detail history, EN/BM stage/next-action copy, focus/action refresh and at most six visible pending-work checks per sign-in. Review deadlines are informational; expiry does not automatically reject anyone. No opaque percentage or hire probability is shown. After a stale-version error, refresh and review before retrying.

Rollback means disable progression UI/new actions while retaining canonical IDs, snapshots and audit history. Do not drop the shadow schema or restore unsafe legacy endpoints/passwords/public uploads. Live backup/restore, Auth/RLS/Storage, proxy SSE/cookies and hosting budgets stay pending in M1/M2 GATE.md until configured. Run tests at phase completion only; gate fixes receive affected reruns.
