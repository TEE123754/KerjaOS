# Privacy operations and release approvals

The EN/BM versioned demo notice is served at `/api/v1/privacy/notice` and shown in the privacy centre. It names synthetic-only use, purposes, human decisions, private practice, disabled official providers, incomplete automated portability and pending contact/transfer/retention approval. It does not claim legal compliance. PRIVACY_CONTACT is not a fabricated address; missing contact visibly defers public release.

Candidate tokens alone select their own export rows; no requested actor ID or staff notes endpoint exists. Fourteen sections are paginated at 100 rows, with next_offset (follow until null; an exact 100-row final page may require an empty next page). Exports are authenticated no-store JSON attachments. A section page is a scoped convenience export, not a complete statutory access determination. Staff notes/question keys, raw files, identity assertions/shares, background disputes/reviewer details and some service/audit data require separate lawful access review. Existing authenticated document access is distinct. Store downloaded data privately and delete it when no longer needed; the app cannot remotely erase downloads.

Requests: access, correction, erase_private_workspace, erase_account. UUID idempotency, maximum ten pending requests per account; records contain only necessary user rationale (never paste IDs/reports/passwords). Candidate cannot choose another owner or mark a request approved. The operator reviews purpose and lawful exemptions/retention privately. Candidate UI shows pending_review, not deleted. Review queue/aggregate is operator-only, with no broad browser admin request listing.

For explicit private workspace erasure, an authorized operator reviews the request then invokes service-only `m9_approve_private_erasure(request UUID)`. It atomically deletes owned practice attempts, saved jobs, external tracker notes and eligible minimal chat metadata, writes a cutoff ledger and marks private_workspace_erased. Real applications, quiz results, consent, final decisions, identity/background and audit history are retained for separate review. Unexpired external chat reservations remain until seven-day expiry to preserve quotas; disclose this exception. A subsequent user-created item is not erased by an older replay. Full account erasure is NOT implemented as an automatic cascade; Auth, business/audit retention and documents require a documented reviewed disposition before completion. Access/correction completion is likewise manual; do not invent a reviewed result.

Document cleanup: existing M1/M3/M5 routines remove encrypted objects first and then mark metadata deleted. M9 captures future tombstones (and existing deleted document keys) in a service-only ledger. A restore must use the newest ledger, not just the older backup's ledger. M9 erasure replay is scoped; post-backup consent/identity-sharing revocation and business event reconciliation still require latest reviewed records. Never restore traffic until those checks pass.

Metadata: existing chat cleanup purges expired records. Service-only m9_metadata_cleanup deletes seven-day-old cancelled/finished reminders. There is no automatic recurring worker; operator must schedule and measure bounded runs before public availability. Use operations_m9 aggregate to detect overdue documents/dead letters/privacy requests. Keep request/event/scorecard/consent ledger retention on explicit review; do not auto-purge legal audit records with guessed deadlines.

No real-data activation until reviewer/date/evidence recorded. These are approval requirements, not legal advice or a claim that engineering tests establish compliance.
