# M4 — versioned quiz and private readiness practice

M4 restores the original screening/practice/report capabilities through the secure per-application foundation. Legacy CandidateSandbox, mutable shared banks, paid/model grading and legacy Report Agent remain retired. The new offline report endpoint uses only the selected private practice attempt. No AI API key or additional dependency is needed.

## Setup and demo

Run the M1 API/frontend locally and configure Supabase as described in docs/m1/SETUP.md. After the configured backup/restore and live M1–M3 gates, apply `20261002135810_m4_quiz_practice.sql` after the preceding migrations. No remote migration was applied during construction. Backend FastAPI/Pydantic + Supabase PostgreSQL RPC/RLS, React/TypeScript/Vite frontend, existing free pytest/PGlite/Playwright tooling. Hosting remains Vercel/Railway/Supabase; no hosted model/Redis/browser worker added.

An active HM/admin membership, job assignment and verified MFA are required to publish and review. In the quiz panel publish **two separate versions**, one practice and one real, for a published role. Author competency names, prompts, visible assessment rubrics, objective options/answer key and subjective maximum points. Versions cannot be edited through client APIs; publish a new UUID version. At most 20 authored questions, 1–20 randomly selected per attempt, 5–120 minutes. Use at least three objective questions for a numeric practice readiness index. The answer key is never returned by any candidate/staff quiz DTO. Do not put correct answers or private personal data in visible prompts/rubrics.

Synthetic demo: candidate takes practice, changes answers, waits for autosave, reconnects, submits and opens the private index/components/missing-input/roadmap report. Employer cannot fetch the attempt/report and does not see practice in the review queue. Complete M3 identity and separately advance the candidate's application to P3. Start the independently published real version, submit, then use assigned HM MFA to review objective totals and score each subjective answer against the frozen rubric. Human approval creates 30-day quiz evidence; **a separate human pipeline action advances P3**. There is no automatic rejection/shortlist. An ungraded subjective practice answer is flagged as missing human feedback, never counted as a model score. No hiring probability is computed.

Candidate can request extra time or a retake without medical details. Requests are visible to the owner/assigned HM. HM can add 5–120 minutes before a live real deadline (maximum four hours from start), or authorize one retake after submission. Maximum three real attempts per application. Requests before the initial attempt may be recorded; a timed accommodation is granted on the active attempt. Untimed/alternative interview arrangements require manual coordination; no fabricated fulfilment. Consumed retake approvals cannot be reused; a new attempt revokes earlier quiz evidence. Practice is limited to 20 starts/day/account and never consumes real retake permission.

## Clock, reconnect and concurrency

Question selection/order and deadline are stored server-side. Browser countdown is a display based on server time + monotonic elapsed time. Autosaves are debounced/serialized in memory, use optimistic revisions, and store only selected question IDs with bounded answers. If offline, edits stay in component memory with an unsaved warning; reconnect explicitly reloads saved answers (confirmation before discarding). No tokens/answers/reports in localStorage. Refresh/reopen survives with persisted answers; closing the tab before a successful autosave loses unsaved edits.

Server-time expiry is authoritative: save/submit after deadline finalizes only previously saved answers and ignores late input/local revision. Closing the browser does not extend the deadline. Expiry is finalized on the next candidate save/submit/reconnect countdown, or assigned HM uses “Finalize if deadline expired” for an abandoned real attempt. That action checks the server clock and uses saved answers only; it is idempotent and cannot extend/rewrite a submission. No always-on scheduler is required. Raw GET displays the stored active state until finalization. Double submit returns the immutable submission; stale pre-deadline autosave/review/adjustment conflicts. Actual multi-connection locking still needs hosted PostgreSQL validation; serial WASM fixtures do not prove contention.

Optional model scoring remains off: no weights/prompts/API routes installed. Any later activation requires pinned free model, EN/BM golden/paired fixtures, injection testing and human recommendation-only review. Future probability requires lawful consented outcomes, representative role-specific samples, held-out calibration and fairness/uncertainty review; no data collection/training is active. Readiness is bounded objective earned/possible ×100 (minimum three objective questions); unanswered objective questions count zero and appear as missing inputs. Bands: below 50 developing, below 75 building, otherwise ready_for_more_practice. Subjective feedback and missing objective inputs are disclosed separately; the index is not a hiring decision or all-round competence rating.

## Rollback / remaining live gate

To pause new real starts, privileged operator sets `kerja_private.quiz_policy.real_enabled=false`; practice can remain enabled independently. Preserve immutable versions, answers, audit history and reviewed evidence. Existing saved/submitted attempts remain readable/reviewable and active ones may finalize; don't drop tables or expose keys. Reverting API/UI should keep M4 quiz prerequisite enforcement and M3 revocation guards.
